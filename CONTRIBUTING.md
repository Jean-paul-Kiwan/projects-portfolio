# Portfolio contribution guidelines

Keep every project easy to understand, reproduce, and evaluate without inflating its scope.

## A project page should explain

1. The problem and intended user.
2. The context and the author's actual contribution, crediting collaborators.
3. Features present in the source, separate from planned work.
4. Technologies, architecture, installation, and configuration.
5. Test commands and results that were actually obtained.
6. Demonstrations with synthetic data, known limitations, attribution, and license status.

Use one repository for each substantial independent application once it is ready to stand alone. Keep academic indexes and exercise collections lightweight. Avoid duplicating active source code across collections.

## Before adding files

Check ownership and sharing permission. Review secrets and personal data in the files and their Git history. Exclude local environments, credentials, generated dependencies, binary archives, real databases, and restricted course or employer materials. Preserve existing notices. Do not assign a new license to content whose ownership is unclear.

A public portfolio entry does not require the release of company source code. An approved technical overview can describe the problem, personal contribution, approach, and outcome without disclosing implementation details.
